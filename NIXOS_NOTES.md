# PortProtonQt на NixOS: технические заметки

Документ описывает, **почему** пакет пришлось дополнять правками и как именно
диагностировалась каждая проблема. Полезно, если апстрим что-то изменит и
ошибки повторятся.

## Общая схема

```
nix run .#portproton
        │
        ▼
  steam-run (FHS на bubblewrap)          ← nixpkgs, проприетарный
        │
        ▼
  portprotonqt (PySide6, env-python3)    ← GUI
        │
        ▼
  start.sh + functions_helper            ← bash-движок PortProton
        │
        ▼
  pressure-vessel → GE-Proton / Wine     ← качает сам, внутри FHS
        │
        ▼
  игра
```

Две среды, и это главная сложность:

- **GUI** — обычный Nix. Есть `env` с python, PySide6 и всеми зависимостями.
- **Движок** — FHS-окружение. Качает и компилирует Wine/Proton, поэтому нужна
  настоящая система с glibc, bash, `sed`, `tar`, ядром и `/usr`.

`steam-run` даёт второе. На NixOS его приходится запускать вручную, и все
проблемы возникают на стыке этих двух сред.

## Проблема 1: `python3` в скриптах движка

### Симптом

```
ModuleNotFoundError: No module named 'babel'
```

А потом, после починки, следующий:

```
ModuleNotFoundError: No module named 'orjson.orjson'
```

### Причина

`steam-run` **перетирает `PATH`**. Внутри песочницы он выглядит так:

```
/run/wrappers/bin:/usr/bin:/usr/sbin:...
```

Наши пути из nix-store оказываются в хвосте, и `python3` резолвится в
интерпретатор **из FHS-образа `steam-run`**, а не из нашего env.

Дальше работает характерный эффект: чужой интерпретатор версии 3.13 подхватывает
чистые модули (`babel`) с нашего `PYTHONPATH`, но **не может загрузить
скомпилированные** (`orjson`, `pyside6`) — не совпадает ABI-тег расширения.

### Что не работает

Подсовывание зависимостей через `PYTHONPATH`. Для чистых модулей срабатывает,
для скомпилированных — принципиально не может: `.so` собран под конкретную
сборку CPython.

Изменение `PATH` в обёртке тоже не помогает: `steam-run` перезапишет его
после этого.

### Решение

Не полагаться на `PATH` вообще. В установленных скриптах движка (`start.sh` и
`functions_helper`) все вызовы вида

```bash
python3 -m portprotonqt.scripts_utils.idle_inhibit
```

заменяются на абсолютный путь к интерпретатору из env:

```bash
/nix/store/<хэш>-python3-3.13.15-env/bin/python3 -m portprotonqt.scripts_utils.idle_inhibit
```

Таких вызовов всего восемь, все они идут после пробела, поэтому достаточно
плоской подстановки в `postInstall`:

```nix
for f in "$out/share/portproton/scripts/start.sh" \
         "$out/share/portproton/scripts/functions_helper" ; do
  substituteInPlace "$f" \
    --replace "python3 -m portprotonqt" "${python}/bin/python3 -m portprotonqt"
done
```

> `functions_helper` указывается явно: у него **нет расширения `.sh`**, глоб
> `*.sh` его пропускает.

## Проблема 2: `makeWrapper` и двоеточие

### Симптом

Те же ошибки импорта, хотя `PATH` выглядит правильным.

### Причина

`makeWrapper` использует `:` как **разделитель аргументов**, а не как часть
значения:

```nix
# НЕВЕРНО: значение разорвётся на "путь1" и мусор "путь2"
--prefix PYTHONPATH : "$out/lib/python3.13/site-packages:${python.sitePackages}"
```

В итоге в обёртку попадал только первый элемент, второй молча терялся.

### Решение

Передать разделитель отдельным аргументом:

```nix
--prefix PYTHONPATH ':' "$out/lib/python3.13/site-packages"
```

### Смежная ловушка: `python.sitePackages` относительный

Для `withPackages`-сборки этот атрибут раскрывается в **относительный** путь:

```
lib/python3.13/site-packages
```

а не в абсолютный. В `PYTHONPATH` он бесполезен — разрешается от текущего
каталога. Если он всё же нужен, пишем явно:

```nix
"${python}/lib/python3.13/site-packages"
```

## Проблема 3: `kill_portwine` убивает собственный контейнер

### Симптом

Игра не запускается, GUI показывает отчёт о совместимости и
`Exit code: 1`. В логе:

```
bwrap: execvp true: No such file or directory
```

### Настоящая причина

Ошибка про `true` — **отвлекающая**. Реальная причина находится глубже и
проявляется кодом возврата:

```bash
$ echo $?
137        # 128 + 9 = SIGKILL
```

`kill_portwine()` в `functions_helper` ищет bwrap так:

```bash
bwrap_pids=$(pgrep -f wrap | grep PortProton | head -n 1)
```

и шлёт ему `kill -n 9`. **Под `steam-run` этот bwrap — наш собственный
контейнер**, в котором выполняется скрипт. У него стоит `--die-with-parent`,
поэтому сессия умирает мгновенно, ещё до старта игры.

Отсюда и `execvp true`: это уже следующий запуск, когда процесс-контейнер
уже убит и pressure-vessel стартует «снаружи» в неполном окружении.

### Решение

Перед циклом `kill` выкинуть все bwrap-PID, являющиеся предками текущего шелла:

```bash
_pw_collect_ancestor_pids() {
    local pid=$$ ppid out=""
    while [[ -n "$pid" && "$pid" -gt 1 ]]; do
        ppid=$(ps -o ppid= -p "$pid" 2>/dev/null | tr -d '[:space:]')
        [[ -z "$ppid" ]] && break
        [[ "$ppid" == "0" || "$ppid" == "$pid" ]] && break
        out="$out $ppid"
        pid=$ppid
    done
    echo "$out"
}
```

используется `ps -o ppid=`, а не разбор `/proc/<pid>/stat`: поле `comm` в
`stat` заключено в скобки и может содержать пробелы, так что наивное
разбиение по whitespace ломается.

Вставка идёт в `postInstall` перед единственным якорем:

```bash
for pw_kill_pids in ${bwrap_pids} ${wine_pids}; do
```

> Блок передаётся в `awk` через **переменную окружения**, а не через `-v`:
> `awk -v` переинтерпретирует escape-последовательности в значении, и обратный
> слэш в payload молча испортился бы.

## Ложный след: `bwrap: execvp true`

Эту ошибку стоит разобрать отдельно, потому что она тянет на ложное решение.

pressure-vessel делает пробный запуск `bwrap` с `--ro-bind /usr /usr` (то есть
берёт **хостовый** `/usr`) и командой `true` — просто чтобы проверить, работает
ли изоляция. На дистрибутивах с FFS-раскладкой в `/usr/bin/true` есть, на NixOS
нет: `/` почти пуст, всё лежит в `/nix/store`, а `/usr` — симлинки на
`/run/current-system/sw`.

Отсюда соблазн создать `/usr/bin/true` через root. **Это не нужно**: под
`steam-run` `/usr` берётся из FHS-образа, где `true` есть, и ошибка не
воспроизводится. Лечить симптом вместо причины — значит получить рут, которого
задача не требовала.

Проверено: с правильным интерпретатором и защитой `kill_portwine` эта ошибка не
возникает.

## Ловушка версий runtime

PortProton хранит движок в каталоге, имя которого задаётся переменной:

```bash
export PW_LIBS_VER="_v3.0.20260218"
```

Функция `pw_check_and_download_runtime` проверяет наличие **всего двух** файлов:

```bash
${PW_WINELIB}/runtime/files/bin/vkcube
${PW_WINELIB}/pressure-vessel/bin/pressure-vessel-wrap
```

Если оба на месте — перекачки не происходит, **независимо от того, что внутри
лежит**. Поэтому в каталог `libs_v3.0.20260218` можно положить совершенно
другой runtime, и PortProton будет считать, что всё в порядке.

Как проверить, что внутри:

```bash
cat <каталог>/VERSIONS.txt
# depot / pressure-vessel / scripts / sniper — с версиями
```

Ожидаемое содержимое для `libs_v3.0.20260218`:

```
depot              3.0.20260218.209091
pressure-vessel    0.20260218.0
sniper             3.0.20260218.209091
```

Если там другая генерация runtime (например, `steamrt4` и `pressure-vessel`
за `0.2026xxxx`) — каталог подменён. Лечится просто: убрать каталог и дать
PortProton скачать нужный самому.

## Насколько это нативно для NixOS

Честная оценка по слоям.

**Нативно (идеально):**

- Сборка через Meson из исходников апстрима, стандартный `stdenv`, все
  зависимости — из nix-store. Ровно так, как должен собираться любой Python-GUI
  на NixOS.
- Python-зависимости через `python313.withPackages`: канонический способ,
  полная герметичность.
- FHS-слой через `steam-run` — существующий пакет nixpkgs, без самодельной
  сборки. Это лучшее из доступного: FHS на NixOS в принципе не-native, и
  `steam-run` — официальный ответ экосистемы на эту задачу.
- Никаких `substituteInPlace` по исходникам Python, никаких патчей C-кода.

**Не native, но с честным обоснованием:**

- Три правки установленных bash-скриптов. Это хрупко: апстрим переименует
  вызов или сдвинет якорь — и всё развалится. Поэтому обе правки снабжены
  проверками, падающими на **сборке**, а не у пользователя.
- Сам принцип «скрипты на bash, которым нужна настоящая ФС», — это ограничение
  самого PortProton, а не NixOS. Пока движок остаётся bash-скриптом, FHS неизбежен.
- `version = "1.4.1"` при сборке с ветки `main` — расхождение намеренное, ради
  свежих NixOS-фиксов апстрима.

**Что было бы по-настоящему нативно:**

Правки в самом апстриме. Тогда пакет станет обычным `buildNpmPackage`-уровня
выражением без `postInstall`-хаков. До тех пор пор сообщить наверх — хотя бы
пункт про `kill_portwine` это баг независимо от дистрибутива: убийство собственного
контейнера ломается везде, где PortProton запускают внутри bwrap, будь то
`steam-run`, flatpak или gamescope.

## Порядок диагностики

Если что-то снова сломалось, порядок проверенный:

1. **Код возврата.** `137` — контейнер убит, смотри `kill_portwine`. Любое
   другое значение — идём дальше.
2. **Хвост `PortProton.log`.** Это первое, что стоит приложить к багрепорту.
3. **Изолированная проверка интерпретатора** — без GUI и без запуска игры:

   ```bash
   out=$(nix path-info .#portproton)
   env PYTHONPATH="$out/lib/python3.13/site-packages" \
       "$(nix eval --raw --impure --expr '...')" \
       -c "import orjson, babel, portprotonqt"
   ```

4. **Версии runtime** — `VERSIONS.txt` в каталоге `libs_*`.
5. **Окно не видно, но процессы живы** — проверить рабочую область
   оконного менеджера, а не искать баг в Wine. В niri:

   ```bash
   niri msg windows
   ```
